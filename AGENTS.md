# Project instructions

## Resource library work

When the user provides a resource file/link and its name (for example, **"I created a new resource, here it is"**), or asks to add, update, replace, retire or audit a guide/tool, read [resources/SOP.md](resources/SOP.md) before acting. It defines the required Notion, catalogue, landing-page, publishing, live-testing and cleanup workflow. Use [resources/README.md](resources/README.md) for implementation details; older approval wording there does not override this default. A request explicitly limited to an audit or advice remains read-only.

- **Default: do the entire scoped job autonomously.** The user's file/link plus name authorizes creating or updating the Content Assets record, preparing public delivery of that supplied resource, building the page/library, committing and pushing, live testing and deleting only test data created for that run. Do not require a pre-existing Notion record, cover, LinkedIn post, preview or publication approval. This standing instruction replaces the earlier preview-first resource workflow. If the user explicitly requests a preview, show it and honor that review boundary before publishing.
- Fetch the current **LinkedIn Content Hub → Content Assets** schema and existing examples; deduplicate before creating. Codex fills the resource and website/gate fields and links any supplied promoting post. The user supplies only the file/link and name; a cover, post link and audience note are optional. Check current create/edit access; never assume it persists between sessions.
- Read the actual file/tool, verify anonymous access and handle Google Drive **Anyone with the link → Viewer** sharing when permitted. If sharing cannot be changed, give exact clicks. For an attached PDF, use the site's existing public-file delivery convention or host the supplied PDF in the repo. Never ask the user to fill routine Notion fields or perform steps Codex can safely complete.
- `resources/catalogue.json` supplies the website; rebuild generated HTML with `scripts/build-resources.cjs`. Build/test locally, publish, verify the actual live page, test all SOP scenarios, clean up and finalize Notion. Stop only for a real blocker or ambiguity that cannot be resolved safely; continue independent work. Never mark failed or untested work live/complete.
- Keep public copy specific: guide, assessment, toolkit or tool. Resources is the collection/navigation name.
- Reuse the existing form, remembering and Apps Script bridge. Company website is the `company` request field and Notion `Company` text property; `website` is the hidden honeypot. Keep secrets in Apps Script Properties.
- Preserve first-page attribution, per-email return markers and durable pending request IDs. When changing that contract, follow [apps-script/RELIABILITY-UPDATE.md](apps-script/RELIABILITY-UPDATE.md): the backend and Notion `Request IDs` text property must be ready before the retrying frontend is published.
- Preserve the latest-20 request-ID limit and keep queue sending in the main page, not its embedded assessment. New resources normally reuse the existing backend/deployment; no new secret or deployment is needed.
- Do not mark work complete until the applicable SOP checklist passes. Clearly distinguish a local preview, a published change and a verified live result.

Report the live landing-page link, confirm live testing only when every applicable check passed, and give a three-line summary. Apply the same end-to-end default to updates and retirements, preserving history and handling old URLs. These instructions do not authorize unrelated website edits, outreach/posting, unrelated Notion changes or deletion of real signup history.
